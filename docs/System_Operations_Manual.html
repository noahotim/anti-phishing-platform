1  System overview

PhishGuard is an internal, self-hosted anti-phishing platform. It inspects URLs before employees click them, detects look-alike / typosquatted / homoglyph versions of your trusted brand domains, cross-checks destinations against a continuously refreshed threat-intelligence repository, and — when a policy is configured — stops whole categories of sites (betting/gambling, adult content, social media) from opening in the browser.

Capabilities

  • URL analysis — full decomposition, IDN/UTS-46 normalisation, Unicode homoglyph folding, mixed-script detection, edit-distance typosquatting, TLD-confusion, brand/subdomain embedding, and public-suffix-aware domain matching.
  • Threat intelligence — a keyless live feed (abuse.ch URLhaus hostfile) synced on a schedule into a local repository, plus optional keyed per-scan providers (VirusTotal, Google Safe Browsing, URLhaus API).
  • Content policy — block categories of websites org-wide; lift a category any time from the console.
  • Warning interstitial — a browser warning page stops employees from proceeding; analysts/admins can override after review.
  • Email analysis — sender impersonation, display-text-vs-href link mismatches, risky keywords and attachments (API ready for gateway integration).
  • Reporting & triage — employees can report suspicious links; analysts/admins triage them to resolution.
  • Admin console — dashboard, reports, trusted domains, blocked sites, audit log, users, settings.
  • Security built in — PBKDF2-HMAC-SHA256 password hashing, revocable bearer sessions, role-based access control, per-route rate limiting, SSRF-safe analysis (URLs are never fetched), full audit trail, strict CSP.
How the platform is used in practice. An employee pastes a link into the checker (or a gateway calls the API). The platform returns a verdict (SAFE / SUSPICIOUS / MALICIOUS / UNKNOWN) with a 0–100 risk score. If the link is blocked, the employee is sent to the warning page instead of the site. All activity is recorded in an audit log and can be escalated into a phishing report.

3  Installation & configuration

Requirements

  • Python 3.12+ (developed on 3.13) on Windows / macOS / Linux.
  • No other services — SQLite is the standard library.

Install steps

cd backend
py -m venv ../.venv                     # create virtual environment
..\.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env                  # then edit .env (see Appendix A)

Configuration

Everything is configured through environment variables or a backend/.env file, loaded at import time via python-dotenv. Secrets must be set there, never hard-coded. The full reference is in Appendix A. Key operational switches:

4  Starting & running the system

Run the server (development / live)

cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000

The uvicorn process performs the following on startup:

  1. Loads configuration from .env.
  2. Initialises the SQLite database (creates tables; runs the schema migration for existing databases — e.g. adding known_threats.category).
  3. Seeds the database if SEED_ON_STARTUP=true (organisation, super admin, trusted domains, demo blocked sites).
  4. Starts the background threat-intel sync task if TI_SYNC_ENABLED=true (first sync immediately at startup, then every interval).
  5. Serves the API and the static frontend.

Runtime logsUvicorn logs go to the console; when run as a background service, to the configured out/err log files.

5  User workflows

5.1 Checking a link

  1. An employee opens http://<host>:8000/app/index.html and signs in (default demo admin — see Appendix C; other users are created by a super admin).
  2. They paste a URL into the checker and submit. The browser calls POST /api/analyze/url.
  3. The server runs the full detection pipeline (Section 6) and returns the verdict, risk score, matching signals, and human-readable reasons.
  4. The checker UI renders the result. If the verdict is blocked (MALICIOUS from malware/threat-feed, or an active content-policy block), the UI can redirect to /app/warning.html?url=…&scan_id=….

5.2 The warning page

AudienceBehaviour
EmployeesSee the red/orange warning; cannot continue. The “continue anyway” action is hidden; they are told to go back and verify with the security team.
Analysts / admins / super adminsThe warning can be overridden for a test, since these roles have verified-review responsibility.

The warning page shows the exact URL, the risk score, what brand is impersonated (when known), and the reasons. For policy blocks it displays a distinct “Access blocked by organization policy” banner with the category (e.g. Gambling / betting).

5.3 Email analysis service

An API-ready service: POST /api/email/analyze accepts a raw email and evaluates sender impersonation (a display name / domain matching a trusted brand), link display-text-vs-href mismatches, risky keywords, and risky attachments. It returns the same verdict/score/reasons model. This is designed for a mail gateway integration.

5.4 Submitting a phishing report

Any signed-in user can create a report (POST /api/reports). The reported URL is re-analyzed under source=REPORT. Analysts/admins then triage it from NEW → INVESTIGATING → CONFIRMED_THREAT / FALSE_POSITIVE → RESOLVED. Employees only see their own reports; analysts and admins see org-wide ones.

6  How the analyzer works

The analyzer is the heart of the platform. For every submitted URL it runs a deterministic pipeline (no content is ever fetched — the target server is never contacted).

6.1 Pipeline stages

StageWhat it does
1. URL decompositionSplits scheme, host, port, credentials, path. Extracts the registrable domain and TLD using real public-suffix rules. Punycode is decoded.
2. NormalisationUTS-46 (IDNA) mapping: case-folds, maps confusable code points, builds the ASCII/punycode form.
3. Homoglyph foldingFolds Unicode confusables to a canonical ASCII form (circled letters, look-alike Latin/Cyrillic characters, etc.).
4. Mixed-script / oddity checksDetects mixed scripts, excessive/odd characters, IP-literal hosts, credential abuse.
5. Trusted-domain comparisonCompares the destination against the organisation’s trusted domains: exact matches, edit-distance typosquatting, TLD confusion, misleading subdomains, suffix embedding, brand prefixes, circled-letter variants.
6. Threat-intel checkChecks the destination against the local known_threats repository (feed + manual + seed) and, if enabled, keyed per-scan providers (Section 7).
7. Risk scoringAggregates weighted signals into a 0–100 score and a classification band; produces human-readable reasons.
8. Policy overrideIf the host matches a blocked site whose category is active in the org content policy, forces MALICIOUS / 100 with a policy reason (Section 8).

6.2 Signals & reasons

Each scan carries a signals object and a reasons list. Example signals: exact_match, trusted_exact, matched_domain, edit_distance, confusable_exact_match, untrusted_destination, content_blocked, blocked_category. Reasons are human strings such as:

  • “Destination domain is not an approved domain”
  • “Domain visually matches approved domain ‘example.com’ (confusable homoglyphs)”
  • “Confirmed malicious by threat intelligence” / “Domain matches known malicious host”
  • “Blocked by organization policy — GAMBLING websites are not allowed”

6.3 Classification & thresholds

Condition (risk score)VerdictSuggestion
≤ low thresholdSAFECan visit (when no caveat)
≤ moderate thresholdSUSPICIOUSWarn before visiting
≤ high thresholdMALICIOUSBlock / report
> high (critical) or known-threat hit or policy blockMALICIOUS (score 100)Block / report
Signal-driven anomalyUNKNOWNNeeds human review

Threshold defaults: LOW_RISK_THRESHOLD=20, MODERATE_RISK_THRESHOLD=50, HIGH_RISK_THRESHOLD=75. They are editable per organisation from Settings (must satisfy low < moderate < high). The “unapproved destination is never SAFE” rule is safety-first by design.

7  Threat intelligence

7.1 Local repository (known_threats)

Confirmed threats are stored in known_threats and checked for every scan. Rows come from one of three sources:

SourceOriginNever evicted
SEEDDemo data created at first startupYes
MANUALAdmins via the console/API (blocked sites)Yes
URLHAUS_FEEDLive keyless feed (abuse.ch URLhaus hostfile)No — oldest evicted past cap

7.2 Keyless live feed (ti_sync)

  • Downloads the public URLhaus hostfile (https://urlhaus.abuse.ch/downloads/hostfile/) — no API key.
  • Parses both 0.0.0.0 <host> and 127.0.0.1 <host> lines, dedupes, and upserts into known_threats as URLHAUS_FEED.
  • Scheduling: immediate sync at startup, then every TI_SYNC_INTERVAL_MIN minutes via a background asyncio task, cancelled cleanly on shutdown.
  • Idempotent: re-syncing an unchanged feed adds 0 rows.
  • Caps: at most TI_SYNC_MAX_ITEMS per sync; when the table exceeds TI_SYNC_MAX_TOTAL, the oldest feed rows are deleted (never manual/seed rows).
  • Admins can trigger POST /api/threat-intel/sync (logged SYNC_THREAT_INTEL).

7.3 Keyed per-scan providers

Optional (ENABLE_EXTERNAL_TI=true, off by default): VirusTotal, Google Safe Browsing, URLhaus API. Require API keys. Results are cached per scan in threat_intel_results.

7.4 SSRF safety

All outbound TI traffic — the bulk hostfile download and the keyed per-scan providers — goes through the SSRF guard in services/ssrf.py:

  • Only a fixed allow-list of TI hosts may be contacted (e.g. urlhaus.abuse.ch, phishstats.info, the keyed provider base URLs).
  • HTTPS only, connection timeouts, redirects re-validated per hop and rejected if they leave the allow-list.
  • The analyzer itself never fetches user-supplied URLs — SSRF is structurally impossible.

8  Content policy & blocked sites

The content-policy feature lets an organisation block whole categories of websites — for example betting/gambling — in the browser. It works through the same scan/warning flow as malware.

8.1 Categories

CodeLabel shown to users
GAMBLINGGambling / betting
ADULTAdult content
SOCIAL_MEDIASocial media
OTHEROther blocked content
(empty)Uncategorized — always treated as malware, regardless of policy

8.2 Enforcement model

  • A blocked site is a known_threats row, optionally carrying a category.
  • Uncategorized rows are unconditional malware. They block every scan.
  • Categorized rows are enforced only while that category is active in the org content policy (stored as JSON under system_settings, key content_policy; default ["GAMBLING","ADULT"]).
  • When a scan hits an active categorized entry, the analyzer forces MALICIOUS / score 100 and returns content_blocked=true, blocked_category, and the policy reason.
  • The warning page renders a dedicated Policy block banner with the friendly category label.
  • Toggling a category off in Settings lifts the block immediately for those categorized sites (uncategorized rows stay blocked).
  • Matching is done on the exact registered domain and its subdomains (no broad TLD matches), making bypass via subdomains impossible.

8.3 Managing from the console

The admin console has a Blocked sites tab:

  • Content policy card — checkbox the categories that should be blocked, save.
  • Add a blocked site — domain + category (leave category empty = malware/always blocked) + note.
  • Import CSV — columns domain[,category[,note]]; an optional header row is skipped; result reports added/skipped/errors.
  • List / edit / delete — filter by category, edit category/note, unblock.

Every mutation is audited: CREATE_BLOCKED_SITE, UPDATE_BLOCKED_SITE, DELETE_BLOCKED_SITE, IMPORT_BLOCKED_SITES, UPDATE_CONTENT_POLICY.

8.4 Browser guard — automatic blocking (no link-pasting)

The PhishGuard browser extension (Manifest V3, Chrome/Edge) makes blocking automatic: every site a user opens is checked against the platform before it loads, and blocked pages are redirected to the same warning interstitial. Users never have to paste a link into the checker.

Two layers work together:

  • Instant network layer. The extension pulls GET /api/guard/rules (manual + seed blocked domains, filtered to the categories currently active in the content policy) and installs declarativeNetRequest redirect rules. Known bad/policy pages are stopped at the network level — they can’t even begin loading.
  • Per-navigation check. Every top-level http(s) navigation is sent to POST /api/analyze/precheck — anonymous and side-effect-free (no scan rows, no audit). Blocked verdicts redirect the tab to /app/warning.html?blocked=1&url=…&label=…&reason=…, which renders for signed-out users too. A 10-minute host cache keeps traffic near one request per new domain.
Behaviour notes. The guard never blocks the platform itself, only top-level pages (sub-frames/ads are untouched), fails open while the server is unreachable, can be paused for 15 minutes from the popup, and by default blocks only MALICIOUS verdicts (a “also hold SUSPICIOUS” option exists). The long tail — threat feed hosts, typosquats, homoglyphs — is caught by the per-navigation check in both layers. Deploy via chrome://extensions → Load unpacked pointing at extension/, configure the server URL in the extension Options, then distribute fleet-wide with an enterprise ExtensionSettings policy (see extension/README.md).

9  Phishing reports & triage

  1. An employee clicks Report on a suspicious result (or submits a URL directly via POST /api/reports).
  2. The system re-analyzes the URL under source=REPORT and stores the report as NEW.
  3. An analyst or admin opens the Phishing reports tab and reviews the full analysis (verdict, score, reasons).
  4. They change the status: INVESTIGATING → CONFIRMED_THREAT (or FALSE_POSITIVE) → RESOLVED.
  5. Status changes are audited, keeping a trail of who decided what and when.
Reports can be filterable by status (all statuses are visible to analysts/admins; employees only see their own).

10  Users, roles, authentication & sessions

10.1 Roles (RBAC)

RoleCapabilities
EMPLOYEECheck URLs, analyze email, report phishing. No management, no dashboard, cannot override warnings.
SECURITY_ANALYSTEverything above, plus dashboard view and report triage; can override warnings; cannot manage domains/blocked sites/settings.
ADMINAnalyst scope + manage trusted domains, blocked sites & content policy, audit log, risk thresholds.
SUPER_ADMINEverything, including user & role administration (create users, change roles, disable accounts, reset passwords).

10.2 Authentication & sessions

  • Passwords hashed with PBKDF2-HMAC-SHA256 (310,000 rounds by default), unique per-password salts.
  • Login returns a bearer token stored by the frontend in localStorage and sent as Authorization: Bearer ….
  • Sessions are revocable: logout revokes the token server-side; disabled accounts lose access; tokens expire after TOKEN_TTL_HOURS (default 7 days).
  • Failed logins are limited (auth rate bucket) and logged as AUTH_FAILED audit entries.
  • On 401, the frontend clears the token and redirects to the login page.

SQLite in WAL mode, foreign_keys=ON, 30 s busy timeout, thread-local connections. All timestamps UTC ISO-8601. Tables:

16  Security model & hardening

  • No SSRF: the analyzer never fetches user URLs; outbound TI is allow-listed + redirect-guarded.
  • Credentials: PBKDF2-HMAC-SHA256, per-password salts; no plain-text storage; secrets only in .env (never in source).
  • Sessions: revocable server-side tokens with TTL.
  • RBAC: every route enforced by role dependencies; employees cannot manage anything.
  • Rate limiting: per-route-group buckets (Section 13).
  • Audit: every mutation and auth event recorded (Section 12).
  • Frontend hardening: strict Content-Security-Policy headers; no inline scripts; all API data rendered through UI.esc() (no self-XSS surface); login/session-expiry redirects.
  • Boundaries: LAN-facing by design; inbound firewall open only on TCP 8000 for the private network.

17  Testing & quality

  • Full pytest suite (134 tests) in backend/tests/, running against a temporary SQLite DB — your real database is never touched.
  • Coverage: URL parser, homoglyphs, similarity, risk scorer, full analyzer dataset, SSRF guard, auth/RBAC, the full HTTP API, rate limiting, email analysis, threat-feed sync, content policy, and browser-guard endpoints (precheck / guard/rules).
  • Frontend and extension JS are syntax-checked with node --check.

18.5 Manual threat-feed sync

Console → Overview → Sync now, or POST /api/threat-intel/sync. The response reports fetched/added/total; idempotent runs report added: 0.

18.6 LAN / firewall

Server binds 0.0.0.0. A Windows Firewall inbound rule (“PhishGuard 8000”, TCP 8000, Allow, Private/Domain) exposes the console to LAN machines at http://192.168.100.43:8000. Leave Public disabled. The browser guard extension talks to the same origin.
